================================================================================
E-NUMERAK — AI ASSISTANT AGENT (PRODUCTION ARCHITECTURE)
================================================================================
Scope   : New role-aware, agentic AI Assistant embedded inside the existing
          E-Invoiceing-for-ASP (E-Numerak) platform.
Backend : Django (new app inside the existing project — NOT the standalone
          FastAPI chatbot; that one stays untouched for public/general chat).
Frontend: Next.js (existing frontend project — new route/components).
Auth    : Reuses existing E-Numerak JWT session. No separate login/register.
Access  : Role-based — Admin view vs Supplier view are structurally different,
          not just hidden/shown UI. Each role gets its own component tree and
          its own scoped tool-set on the backend.

================================================================================
1. HIGH-LEVEL FLOW
================================================================================

  Next.js (logged-in user, JWT in memory/cookie)
        │
        │  POST /api/v1/ai-assistant/chat/   (Authorization: Bearer <JWT>)
        ▼
  Django REST endpoint
        │
        │  1. Authenticate JWT → request.user, request.user's CompanyMember
        │  2. Resolve role (admin / accountant / supplier / viewer)
        │  3. Load ONLY the tool-set allowed for that role
        │  4. Run agent loop (LLM decides which tool(s) to call)
        │  5. Every tool internally re-filters by company_id — never trusts
        │     the model's arguments for scoping, only for intent
        │  6. Write-type tools return a PREVIEW, not a committed action
        │  7. User confirms → second request executes the committed action
        │  8. Every action (preview + commit) written to AIAssistantAuditLog
        ▼
  Streamed response back to Next.js (SSE or chunked, like existing chatbot)

--------------------------------------------------------------------------------
2.1 KEY DESIGN RULE (do not relax this)
--------------------------------------------------------------------------------
Every tool's execute() method signature looks like:

    def execute(self, *, user, company, **model_provided_args):

`user` and `company` come from the AUTHENTICATED REQUEST, injected by the
orchestrator — never from the LLM's tool-call arguments. If the model's
arguments contain a "company_id" or "customer_id" that doesn't belong to
`company`, the tool raises PermissionDenied and logs an AIToolCallLog with
status="error". The model is only ever trusted to express INTENT
("show invoice INV-2026-0012"), never SCOPE (which company that invoice
must belong to).

--------------------------------------------------------------------------------
3.1 ROLE SEPARATION AT THE UI LAYER
--------------------------------------------------------------------------------
`page.tsx` reads the user's role from the existing auth/session context
(already available today for the rest of the dashboard) and renders either
<AdminAssistantView /> or <SupplierAssistantView /> — these are genuinely
separate component trees, not one component with a bunch of if/else. This
keeps future role-specific features from tangling together, and it means a
supplier's bundle never even references admin-only components.

================================================================================
4. AUTH INTEGRATION (no new login system)
================================================================================

- Frontend: reuses the existing JWT access token already stored for the
  main app (same axios/fetch instance + interceptor used elsewhere).
- Backend: reuses existing DRF JWT authentication class already configured
  for the rest of the API (rest_framework_simplejwt) — no new auth backend.
- Role resolution: apps/ai_assistant/permissions.py::get_user_role() reads
  from the existing CompanyMember model (already has `role` field per
  companies/models.py) — no new role system invented.

================================================================================
5. WHERE THIS PLUGS INTO THE EXISTING PROJECT
================================================================================

- config/settings/base.py     → add "apps.ai_assistant" to INSTALLED_APPS
- config/urls.py              → include apps/ai_assistant/urls.py under
                                 /api/v1/ai-assistant/
- requirements/base.txt       → already has openai / groq / anthropic —
                                 no new AI SDK dependency needed
- docker-compose.prod.yml     → NO new service required — this runs inside
                                 the existing `backend` (gunicorn) container,
                                 unlike the standalone FastAPI chatbot
- Nginx                       → NO new route needed — falls under the
                                 existing /api/ location block on
                                 api.e-numerak.com

6. BUILD ORDER (recommended)
================================================================================

  Phase 1 — Skeleton
    1. Django app scaffold (models, migrations, urls, empty views)
    2. Role resolution + permission tests passing
    3. Next.js route + button wired to existing nav, empty shell UI

  Phase 2 — Read-only tools only
    4. Implement read/ tools (invoice lookup, customer lookup, VAT calc)
    5. Orchestrator + LLM client wired, streaming works end-to-end
    6. Admin view + Supplier view both functional for READ-ONLY chat

  Phase 3 — Write tools with confirmation
    7. AIPendingAction model + preview/confirm endpoints
    8. draft_invoice / add_customer tools
    9. InvoiceDraftPreviewCard + confirm flow in UI

  Phase 4 — Hardening
    10. Full audit log review, rate limiting per tool, load testing
    11. Security review of test_tool_scoping.py against real spoofing
        attempts before enabling write tools in production
